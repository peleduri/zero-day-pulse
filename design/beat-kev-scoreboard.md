## Problem Statement

The question is whether Zero Day Pulse can make money. The honest starting point:
- **Nobody is known to rely on it.** Asked who uses it and what they would do without it, the founder said: "I don't know."
- **The obvious product is already free or close to it.** "KEV/EPSS alerts filtered to my stack" is sold by several vendors for $0–7 a month.
- **The open question is whether the project has an edge anyone would pay for.**

## Demand Evidence

None yet. There's a public repo, a public dashboard, and a LinkedIn post. No user has been identified, nobody has paid, and nobody has asked to.

## Status Quo

What people use today (prices are the vendors' listed rates from November 2026, not verified):
- KEV Watch: free weekly digest; a $5/mo tier is announced but not live.
- CVE Alerts (Daily CyberSecurity): free for 3 vendors, $7/mo, $29/mo for teams. KEV + EPSS alerts to email, Slack, Teams or GitHub Issues.
- OpenCVE: free, $19, $49 or $299/mo; also open source.
- SecAlerts: $90–390/mo, priced per "stack"; fits MSPs.
- VulnCheck: enterprise; raised a $25M Series B in February 2026 selling **lead time**, meaning knowing about exploitation before CISA KEV lists it.
- Large companies use Tenable, Qualys or Rapid7 ($50K+/yr). Small teams read CISA KEV, vendor emails and news by hand.

## Target User & Narrowest Wedge

- **Most likely buyer (a guess, not yet tested):** an MSP or a small team covering many stacks. The cost of finding out late shows up as client incidents, and they already pay per stack (SecAlerts).
- **Narrowest wedge:** before selling anything, prove the one claim a buyer would pay for: "Zero Day Pulse sees exploitation N days before CISA KEV."

## Constraints

- Keep it zero-cost to run: GitHub Actions plus Pages, with no new services or secrets.
- Keep the security rules in CLAUDE.md.
- **Measure only from the go-live date.** Earlier runs didn't store when a CVE was first seen, so there's no backfill.

## Premises (agreed)

1. "KEV/EPSS alerts for my stack" is a commodity and won't make money on its own.
2. If money exists, it comes from **lead time** (exploitation seen before KEV) or from **serving many stacks** (MSPs), not from a nicer dashboard.
3. There's no demand evidence yet, so **conversations come before features**.
4. Even if it never becomes a business, the repo has value as reputation: an open-source tool and a public dashboard.

## Approaches Considered

- **A: "Beat KEV" scoreboard.** CHOSEN. Small build, and it proves or disproves the edge.
- **B: Multi-stack service for MSPs.** Deferred. It's a large build with no demand evidence yet. Revisit only if A shows real lead time.
- **C: Open source + reputation.** Not a separate build. The weekly scoreboard post doubles as C's content.

## Recommended Approach (A): decisions

1. **What counts as a signal.** A CVE gets a signal from an entry when **both** of these hold:
   - The entry is not from the KEV feed, and it matches a **zero-day keyword in its own text** (title + summary).
   - The CVE is **not in the KEV catalog loaded on that run**. If the catalog failed to load, record the signal anyway. A CVE that was already in KEV can then only end up with `lead_days ≤ 0`, so it can never land in "earlier".
   - The entry cites **at most 2 CVEs**. Round-ups (Patch Tuesday, monthly roll-ups) cite up to 10, and a "zero-day" word in one of them would otherwise give a signal to all 10.

   This test never uses `in_kev`, `is_kev` or `is_zero_day`. Since #11, `is_zero_day` is also true just because a CVE is in KEV, so using it would count KEV as its own early warning.

   Vendor-advisory wording that the keyword list misses ("exploited" phrased differently) is left to Open Question 3. There's no separate advisory-feed rule.
2. **Where signals are read from.** Signals are taken from **every collected entry before dedup**: after `attach_cve_ids`/`annotate_kev`, before `filter_zero_days`. For each CVE, keep the earliest qualifying entry.

   Dedup in `filter_zero_days` drops repeat copies. If signals were read from the surviving findings, the earliest source would sometimes be lost.
3. **Timestamps.** Each signal records `observed_at` (the run time when the pipeline first saw it) and `published` (the entry's own date; null if missing or unparseable).
   - **Lead time is computed from `observed_at`.** That's what the pipeline actually knew, and it can't be faked by a backdated article.
   - `published` is stored for reference only.
4. **`state/first_signal.json`.** CVE → `{observed_at, published, source, link}`, written only the first time a CVE qualifies.
   - Kept for 180 days, capped at 5000 entries, oldest `observed_at` pruned first.
   - It's separate from the 14-day watchlist, because KEV can list a CVE weeks after the first report.
   - A missing or corrupt `first_signal.json` is treated as empty: log a warning, never crash.
   - `state/kev_scoreboard.jsonl` is read line by line:
     - An unparseable line is skipped with a warning.
     - If a CVE appears on more than one line, the first one wins.
     - If any line was bad or duplicated, the file is rewritten atomically (temp file + rename) from the valid rows before new rows are added. Corruption can never cause rows to be re-added on every run.
   - **Go-live header.** The first line of `kev_scoreboard.jsonl` is always `{"go_live": "YYYY-MM-DD"}`. It is told apart from CVE rows because it has no `cve` key. It's written when the file is first created and never changed, and the atomic rewrite always keeps it as line 1. The catalog walk, the warm-up and the "collecting data since" text all read it.
   - **Recovery when the header is lost:**
     - **File missing:** this is a genuine first run. Create the file with today's date as go-live.
     - **Header missing or unparseable, but valid rows exist:** rebuild the header from the earliest `kev_date_added` among the valid rows, log a warning, and rewrite atomically. Go-live never resets to today while old rows exist, so data can't be re-counted or re-warmed.
5. **Scoreboard rows come from the full KEV catalog, not the lookback window.**
   - The lookback path can miss additions: KEV `dateAdded` has no time of day, so it is effectively 00:00 UTC and falls outside a 24h window after the first run of that day.
   - Instead, every run walks the **whole catalog** from `load_kev_catalog`. Every CVE with `dateAdded` ≥ go-live date that isn't in `state/kev_scoreboard.jsonl` yet gets one row.
   - Row: `{cve, kev_date_added, vendor, product, cve_year, observed_at, source, link, lead_days, bucket}`. It's written once per CVE and never rewritten.
   - Signals are updated **before** scoreboard rows are written in the same run.
   - If the catalog fails to load, no rows are written that run. The next good run catches up, because the catalog walk covers everything since go-live.
6. **Lead time and buckets.** `lead_days` = KEV `dateAdded` minus the UTC date of `observed_at`, in whole days. Every row lands in exactly one bucket:
   - **earlier:** `lead_days ≥ 1`
   - **same day or late:** a signal exists but `lead_days ≤ 0`
   - **missed:** no signal
7. **Excluded from the decision numbers** (still shown as counts so nothing is hidden):
   - **Warm-up:** KEV additions in the first 14 days after go-live. Exploitation news from before go-live was never recorded, so those would count as missed unfairly.
   - **Old CVEs:** the CVE year is more than 1 year before the KEV `dateAdded` year. KEV regularly lists years-old CVEs whose exploitation news no 24h-lookback monitor could have caught.

   The panel shows "N excluded (warm-up / old CVE)".
8. **Numbers.** Two populations are computed separately:
   - **All:** every KEV addition that isn't excluded.
   - **Edge:** the same, limited to KEV `vendorProject` in {Fortinet, Ivanti, Cisco, Palo Alto Networks, Citrix, SonicWall, Check Point, F5, Juniper}.

   For each population, over windows of 30 and 90 days based on `kev_date_added`:
   - additions counted;
   - the **% earlier**, out of all counted additions;
   - the **median and max lead**, over the *earlier* rows only;
   - the counts of same-day/late and missed.

   The panel shows "collecting data since <go-live>" for any window with fewer than 10 counted additions.
9. **Outputs.**
   - A "Beat KEV" panel at the top of the dashboard and `latest.md`, with a caveat line: "Zero-days reported before a CVE ID exists can't be matched and count as missed."
   - The raw numbers go to **`docs/scoreboard.json`**, which Pages serves at `https://peleduri.github.io/zero-day-pulse/scoreboard.json`. `docs/` is already in the workflow's `git add`.
   - All text is escaped and links go through `safe_url`.
   - The weekly post is written by hand from the panel.
10. **Tests the build must cover:**
    - The signal test ignores `in_kev` and `is_zero_day`, a CVE that is already in KEV gets no signal, a round-up citing more than 2 CVEs gives no signals, and a failed catalog load still records signals.
    - Corrupt scoreboard lines are skipped, duplicates removed, and the file rewritten once with no re-added rows. The header is kept on rewrite, and a lost header is rebuilt from the earliest row, not reset to today.
    - Signals are taken before dedup, keeping the earliest entry.
    - Lead days across a UTC date boundary.
    - The three buckets.
    - Write-once rows.
    - A catalog walk that catches additions missed by earlier runs.
    - A failed catalog load writes no rows.
    - Warm-up and old-CVE exclusions.
    - 180-day and 5000-entry pruning.
    - A missing or corrupt `first_signal.json` or scoreboard file.

## Wireframe

```
┌─ 🏁 Beat KEV (last 30 days) ───────────────────────────────┐
│ Counted 24 │ Earlier 9 (38%) │ Median lead 3d │ Same day/late 2 │ Missed 13 │
│ Edge devices: 8 added │ 5 seen earlier │ median 4d                  │
│ Biggest leads:                                                    │
│  CVE-2026-123039 Check Point  +6d  ← Check Point Research         │
│  CVE-2026-104935 Ivanti       +4d  ← Volexity / BleepingComputer   │
└───────────────────────────────────────────────────────────────────┘
│ Excluded: 3 warm-up, 5 old CVEs                                   │
│ Zero-days reported before a CVE ID exists can't be matched and count as missed. │
(shows "collecting data since <go-live>" until a window has 10 counted additions)
```

## Open Questions

- **Do CVE IDs show up in time?** Some zero-days are reported before a CVE ID exists. Those can't be matched later and will count as "missed", which understates the lead. Accept that for now and note it next to the numbers.
- **How precise is a day?** The pipeline runs every 6 hours and KEV `dateAdded` has no time of day, so lead is in whole days and can be off by ±1.
- **Which sources count as signals?** Using only zero-day keyword matches may miss vendor advisories that say "exploited" in other words. Review a sample of misses after 2 weeks.

## Success Criteria

- The scoreboard runs every 6 hours with no manual work, and every KEV addition gets a row (seen earlier or missed).
- **Decision rule after 6 weeks of counted data, or at least 40 counted additions in the All population, whichever comes later.** Use the 90-day window. Check the conditions in this order; the first match wins:
  1. **Edge is real:** Edge has at least 10 counted additions, with **% earlier ≥ 40%** and **median lead ≥ 2 days**, *or* All has **% earlier ≥ 20%** with **median lead ≥ 2 days**. Next step: take the numbers to 5 MSPs (Approach B conversations).
  2. **No edge:** All has **% earlier < 10%**, *and* either Edge has fewer than 10 counted additions or Edge has **% earlier < 20%**. An Edge percentage computed from fewer than 10 additions is never used. With 0 additions it isn't computed at all. Next step: keep the project as open source and reputation (C), and stop chasing revenue.
  3. **Otherwise:** look at which sources produced the "earlier" rows and add more of that kind (vendor advisories, research blogs). Then measure for 4 more weeks and apply the rule again.

### R3-1 — completeness (blocking)

**Problem**

> go_live now lives in a header inside state/kev_scoreboard.jsonl, but the new line-level recovery rules do not cover that header. An unparseable header line is 'skipped with a warning' like any row, the atomic rewrite is 'from the valid rows' (silent on whether the header is kept), and decision 10 still treats a missing scoreboard file as a tested case without saying whether it is a new 'first run'. If the header is lost while rows remain, the design does not say whether go_live is re-stamped to now (which re-applies the 14-day warm-up to live data, shifts the catalog walk start and the 'collecting data since' text, and breaks 'never changed') or recovered some other way. go_live drives the warm-up exclusion and the catalog walk, both of which feed the decision numbers, so this is missing behavior the committed approach needs.

**Remedy**

> Specify the header format (e.g. a first line {"go_live": "YYYY-MM-DD"} distinguished from CVE rows), that the atomic rewrite always preserves it, and the recovery when it is missing or unparseable but rows exist (e.g. fail loudly without writing, or recover from a config constant / git history, never silently re-stamp to now). State that only a fully missing file with no rows counts as a first run. Add the corrupt-header case to the decision 10 tests.

### R3-2 — completeness (minor)

**Problem**

> The 2-CVE cap counts every CVE ID in the entry's cve_ids, which for RSS/Atom are extracted from the whole serialized element (pulse/feeds.py:139, capped at MAX_CVE_IDS_PER_ENTRY = 10), not just CVEs the zero-day wording refers to. A genuine single-target zero-day article that also references a 3-CVE exploit chain or related older CVEs gives no signal at all. Edge-device zero-days (Ivanti, Citrix, Fortinet, Cisco) are often reported as multi-CVE chains, so the cap biases the Edge population toward 'missed' and the decision rule toward 'no edge'. The design does not acknowledge this trade-off.

**Remedy**

> Acknowledge the bias next to Open Question 3, count how many keyword-matching entries were dropped by the cap, and include them in the 2-week review sample of misses; adjust the cap if real chains are being lost.

### R3-3 — consistency (minor)

**Problem**

> Recording signals on a failed catalog load makes a CVE's bucket depend on whether the catalog happened to load. A CVE added to KEV after go-live whose row is still pending (because its catalog load failed) and that is first reported after its KEV addition gets a signal on a failed-load run and lands in 'same day or late', but on a successful-load run it gets no signal and lands in 'missed'. It does not affect % earlier, but it makes the same-day/late and missed counts inconsistent.

**Remedy**

> Accept and state this (it never affects 'earlier'), or define 'same day or late' as including post-addition signals regardless of catalog state.
