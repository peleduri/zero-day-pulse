## Problem Statement

The open issues ask for EPSS and structured exploit data (#2), action-oriented dashboard cards (#3) and a "My Stack" relevance view (#4). Repo evidence shows three problems the issues don't mention:

1. **AI enrichment has produced nothing for at least 16 days.** All 50 committed `latest.json` reports in the fetched history (2026-10-29 to 2026-11-14) have 0 enriched findings. It did work in May: #7's opening report shows "Enriched: 10". In CI run #679, `parallel-cli enrich run` exits 4 right after "Created taskgroup". `pulse/enrich.py:115` logs the *first* 1000 characters of stderr (or stdout), which are INFO lines, so the real error never appears. `requirements.txt` has `parallel-web-tools[all]>=0.0.14`, which is unpinned (CI resolved 0.9.3). That breaks the repo rule "pin with `==`". #3 and #4 as written depend on enrichment fields that are always empty.
2. **KEV detection misses older KEV entries.** `fetch_cisa_kev` (`pulse/feeds.py:197`) downloads the full catalog, then drops every entry added before the lookback window. A CVE that appears in today's GHSA or news feeds, but was added to KEV months ago, is never flagged. "0 KEV" in the latest run means "nothing new was added", not "nothing here is exploited".
3. **The tracker issue is noise.** The workflow comments the full report on #7 every 6 hours (664 comments). #6 is an orphaned duplicate tracker.

## What Makes This Cool

The bot stops being a news feed and becomes **"what changed that I care about"**:
- "CVE-2026-1234 that you saw on Tuesday **just entered KEV**"
- "EPSS for the nginx bug **jumped from 0.04 to 0.61**"
- "**New My Stack hit:** kubernetes"

It does this with no API key, from free, deterministic sources (CISA KEV and FIRST EPSS). The AI enrichment becomes extra detail on top, not something the rest depends on.

## Constraints

- Keep the repo security rules (CLAUDE.md): `defusedxml` only, HTML-escape all external content, block `javascript:`/`data:` URLs (`_safe_url`), secrets only through env vars, pin Python deps with `==`, pin Action refs to SHAs.
- Dashboard stays self-contained: no external JS or CSS (#3 acceptance).
- `my_stack` empty or absent means **#4 adds no stack-related output**: no My Stack section, badges, stat or `new_stack_hit` changes. Intended differences from #2, #3 and #5 still appear: EPSS/KEV badges, In KEV and High EPSS stats, and the "Changed since last run" section when non-empty.
- Must run in the existing 6-hourly Action with no new secrets.

## Recommended Approach (B): decisions

### 1. `pulse/intel.py` (new): deterministic intel

- `load_kev_catalog() -> (raw_records: list, lookup: dict[cve, {date_added, due_date, vendor, product, ransomware}])`:
  - One download per run. Returns `None` on failure, which is distinct from an empty catalog.
  - `fetch_cisa_kev(lookback, raw_records)` is refactored to take the **raw records**, so it keeps building entries from `vulnerabilityName`, `shortDescription` and `requiredAction`. The "new KEV additions" feed behavior stays the same.
- `fetch_epss(cves) -> dict[cve, {epss: float, percentile: float, date}] | None`:
  - Batches of 100, using `requests` (already a dependency).
  - 30s timeout per call.
  - **`None` if any batch fails**, so a partial result is never treated as complete. Logs a warning; never fatal.
- **Findings with several CVEs:**
  - `in_kev` is true if **any** of its `cve_ids` is in KEV.
  - KEV dates and ransomware come from the KEV CVE with the earliest `due_date`.
  - `epss` and `epss_percentile` are the **maximum** across its `cve_ids`.
  - Every CVE is tracked separately in the watchlist (§5).

**Full pipeline order** (`main.py`):

```
collect (feeds + KEV raw records)
  → extract_cve_ids(title + summary) for EVERY raw entry (RSS/Atom included)
  → kev_lookup on those cve_ids                  [sets in_kev before the gate]
  → filter_zero_days (gate + dedup; no sort)
  → fetch_epss for surviving CVEs + watchlist CVEs → annotate (epss fields)
  → sort
  → enrich (top max_enrich of the new sort)
  → stack_match (after enrichment, so affected_products counts)
  → state diff (§5)
  → report
```

- **Fix for old KEV CVEs:** in `filter.py`, `in_kev` counts as a zero-day signal: `is_zero_day = is_kev or in_kev or keyword`. A keyword-less GHSA entry, or an RSS/Atom entry whose summary cites a 2021 KEV CVE, now passes the gate and is flagged. CVE extraction moves out of `filter_zero_days` (`filter.py:42-44`) into this pre-gate step. A test covers a keyword-less RSS entry.
- **Separate field:** `in_kev` is separate from `is_kev`, so `is_kev` ("came from the KEV feed") keeps its meaning for deduplication.
- **Sort key:** uses `in_kev or is_kev`.
  - **Deliberate deviation from #4** ("current sort order unchanged"): old-KEV findings now rise to the top, which is the point of the fix.
  - Otherwise the order is unchanged.
  - The enrichment top-N is chosen from this new sort.

### 2. Stack relevance (#4)

- `config/feeds.yaml` gets `my_stack: []`, empty by default.
- `stack_match(finding, terms) -> list[str]` is case-insensitive and searches title, summary, tags, KEV vendor/product, and enrichment `affected_products` when present.
- **Deviation from the issue: word-boundary matching (`\b` + `re.escape(term)` + `\b`), not raw substring.**
  - Why: substring matching makes `eks` match "weeks" and `go` match almost everything.
  - The issue's own example still passes: `eks` matches "Amazon EKS".
- Each finding gets `stack_match: [...]`, an empty list when nothing matches.
- The **My Stack stat, section and badges are hidden when `my_stack` is empty.**
- **My Stack section** order: in_kev, then EPSS (descending), then zero-day, then recency (per #4).

### 3. Cards and stats (#3)

- **EPSS badge** uses data from FIRST, not the AI: red if ≥ 0.5, yellow if ≥ 0.1, grey otherwise or when missing.
- **KEV badge** on any `in_kev` finding, including old KEV entries. Shows the due date and the ransomware flag.
- **PoC button** appears only when `exploit_available is True` and `_safe_url(exploit_url)` is non-empty.
- **Advisory button** appears only when `_safe_url(vendor_advisory)` is non-empty and the host isn't `nvd.nist.gov` (#3: "vendor page, not NVD").
- **Affected/fixed line** `Affected: X → Fixed: Y` appears only when either field is populated.
- **Stats bar** adds three counts: In KEV, High EPSS (≥ 0.5) and My Stack.
- Cards without enrichment show the KEV/EPSS badges; everything else falls back to today's layout.

### 4. AI enrichment hygiene (#2, AI part)

- **Provisional** pin: `parallel-web-tools[all]==0.9.3`, the version CI resolves today (and which currently exits 4). Replace it after the exit-4 investigation with the version verified locally. Its transitive dependencies stay unpinned; a constraints file is a possible follow-up.
- Log the **last** 2000 characters of stderr and stdout.
- Write the input to a temp file if `parallel-cli enrich run --help` shows a file option. Verify this before changing anything.
- Tighten `ENRICH_INTENT`:
  - `exploit_available` must be exactly `true` or `false`.
  - `exploit_url`, `vendor_advisory`, `affected_versions` and `fixed_version` each get their own field.
  - EPSS stays out of the AI request (it isn't there today).
- `_normalize_enrichment()` handles defensive parsing:
  - Coerces "true (https://…)" to `True` and moves the URL into `exploit_url` when that field is empty.
  - Every URL goes through `_safe_url`.

### 5. "What changed" state and alerts

- **`state/last_run.json`, committed by the workflow.**
  - Contains `{stack_terms_hash, generated_at, run_id, cves: {CVE: {first_seen, in_kev, epss, stack_match}}}`.
  - It is a rolling **14-day watchlist**: every CVE seen in the last 14 days, tracked individually. Cap: 1000 CVEs, oldest `first_seen` pruned first.
- **Each run re-checks the whole watchlist** against the fresh KEV catalog and EPSS scores. The EPSS request covers the stored watchlist plus this run's new CVEs: at most ceil((1000 + new CVEs) / 100) calls, typically ≤ 11. Pruning to the cap happens after the diff.
- **`stack_match` for a watched CVE absent from this run** keeps its stored value. Its inputs (title, summary, tags) aren't stored, so it can't be recomputed.
- **Each CVE stores the `stack_terms_hash` its `stack_match` was computed with.** `new_stack_hit` is emitted only when the stored hash equals the current one (stored empty, now non-empty, same terms). A CVE with a different or missing hash is re-baselined silently whenever it next appears, so a `my_stack` edit never produces a delayed burst of hits.
- **Change kinds**, all compared per CVE against the stored state:

| Kind | Already-watched CVE | First-seen CVE |
|------|--------------------|----------------|
| `entered_kev` | stored `in_kev=false`, now `true` | **no change** (baseline; its KEV badge already shows) |
| `epss_crossed` | stored epss < 0.1 (or < 0.5) and now ≥ that threshold | **no change** (baseline) |
| `new_stack_hit` | stored `stack_match` empty, now non-empty | **emits** if it matches (a new CVE matching your stack is the alert) |

- **Fetch failures never emit changes:**
  - If the KEV catalog is `None`, every CVE keeps its stored `in_kev` and no `entered_kev` is emitted.
  - If EPSS is `None`, every CVE keeps its stored `epss` and no `epss_crossed` is emitted.
  - A stored `epss` of `null` is a baseline, not a crossing.
- **Re-baselining instead of alerting:**
  - When `stack_terms_hash` differs from the current `my_stack`, stack matches are recomputed and stored **without** emitting `new_stack_hit` that run.
  - No state file means the first run is a baseline only: no changes at all.
- **Outputs:**
  - `changes` is written to `reports/changes.json`, stamped with `run_id`.
  - It also goes into `latest.json`, plus a "Changed since last run" section at the top of `latest.md` and the dashboard. The section is omitted when empty.

### 6. Tracker issue (workflow)

- **Target the issue explicitly:** keep today's newest-first `listForRepo` lookup (it picks #7), and filter by the exact title. No "oldest" logic.

  - `reports/changes.json` has `run_id == github.run_id`
  - `changes` is non-empty

  That blocks reposting a stale committed file when a run fails. The comment contains only the change list and @-mentions nobody.
- **Add a workflow `concurrency: {group: zero-day-pulse, cancel-in-progress: false}`** so a scheduled run and a manual run can't race on `state/`.
- **If the state commit or push fails,** no comment is posted. The next run diffs against the last *pushed* state and reports the changes then, so nothing is lost or duplicated.
- Add `state/` and `reports/changes.json` to the workflow's `git add`.

### 7. Tests (none exist today)

  - `_normalize_enrichment`
  - `_safe_url` in the new buttons
